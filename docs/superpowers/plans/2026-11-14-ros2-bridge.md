# Local ROS 2 sensor bridge implementation plan

**Goal:** Receive the D1's verified ROS 1 sensor streams in ROS 2 on the display computer.

**Architecture:** Preserve host Ubuntu 18.04 and vendor Melodic. Use a Linux container with host networking, ROS 2 Humble, and a source-built compatible ROS 1 bridge. Connect to the existing master, never launch another hardware driver.

**Approved approach:** User approved local containers alongside the vendor stack. Modern ROS 2 dependencies remain inside the container. No host OS upgrade or ROS 1 replacement.

## Tasks

- [x] Check runtime, privileges, disk and memory. No Docker/Podman; sudo requires an interactive password. User namespaces work, but rootless Docker prerequisites are missing.
- [x] Prepare `scripts/install-container-runtime.sh`: install Ubuntu's Docker package, start the daemon, verify the engine and a disposable container. No automatic daemon enable or user-group changes.
- [x] Runtime alternative: sudo password unavailable. Existing Bubblewrap and unprivileged namespaces work; use an account-owned Ubuntu 22.04 rootfs instead of Docker. No host package installation required.
- [x] Install Humble and ROS One dependencies. The ROS-O project documents compatibility of the Techfak ROS One repository with official ROS 2 packages. Rootless packaging adjustments documented in README.
- [x] Build the pinned upstream bridge. Initially two jobs; increased to four after observing available memory during compilation.
- [x] Configure an explicit sensor allowlist with ROS 1 to ROS 2 direction only: scan, odometry, IMU, rear RGB/depth, air-quality telemetry, and required transforms. Exclude command, power, disinfection-control and service bridges.
- [x] Run on the host network with `ROS_MASTER_URI=http://192.168.0.4:11311` and `ROS_IP=192.168.0.2`; verify ROS 2 message delivery, timestamps and rates.
- [x] Verify no ROS 1 command publisher was added and motor enable remains false. Document commands and limitations. Ctrl-C stops the bridge; rootfs stays under the user account for reuse.

## Checks and constraints

Container build failure must leave vendor ROS running. No privileged container, device mounts, host ROS mounts, or firmware changes. A successful engine check alone does not establish ROS 2 delivery. Physical stop and watchdog tests remain required before adding drive control. Nav2 and Home Assistant follow after sensor integration.

## Execution evidence

- Official Ubuntu base archive verified against published SHA256.
- Ubuntu 22.04 commands run under Bubblewrap as namespace UID 0, mapped to host UID 1000.
- Host motor-enable parameter remained false during setup.
- Live ROS 2 acceptance check failed with zero messages on all 13 sensor topics before bridge startup, as expected.
- Source build succeeded. Full saved setup script replay also completed with exit 0.
- Live acceptance passed on all 13 topics: 15 Hz scan, roughly 100 Hz odometry/IMU, 28 Hz RGB/depth and 5 Hz air-quality messages. Evidence saved under `docs/evidence/`.
- ROS 2 laser transform resolved; complete TF tree remains unvalidated.
- Graph check confirmed no bridge ROS 1 publishers, unchanged `/cmd_vel` publishers, and motor enable false.
- Fresh review found two setup robustness issues (rootfs override consistency and explicit dependency retry); both fixed before the successful setup replay.
